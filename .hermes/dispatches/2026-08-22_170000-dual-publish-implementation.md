## Verified signing-custody blocker

The existing Ed25519 generator requires `--private-key`. The checked-in production path supplies `DATAPULSE_ATTESTATION_PRIVATE_KEY_FILE` to GitHub Actions; the `datapulse-health.service` environment has no attestation private-key path. The operator-selected migration target is operator-controlled OpenBao Transit, so the production health pipeline must not be changed to copy or expose the GitHub Actions private key.

Consequences:

- a fresh daily Ed25519 chain head cannot safely be generated by the VPS health cycle until production signing custody is deliberately migrated or an approved signer boundary is added;
- dual-publish implementation cannot proceed by silently using a stale `attestations/latest/chain_head.json`;
- the next prerequisite is a production OpenBao deployment/key-custody design and explicit key-material approval;
- production OpenBao provisioning, key generation/import, policy/auth configuration, signing, and Rekor writes remain out of scope for this brief.

## Non-negotiable freshness gate

Before writing any production dual-publish code, resolve and test the source-of-truth question:

1. Which exact canonical daily artifact is signed?
2. Which stage creates it during the same frozen pipeline cycle?
3. How is its digest derived deterministically?
4. How does the existing Ed25519 envelope reference the same digest?
5. How are stale `attestations/latest/*` artifacts rejected?

Do not use an existing `attestations/latest/chain_head.json` merely because it exists. If the current pipeline does not generate a fresh chain head, the implementation must either add a separately tested fresh-generation stage or explicitly block Sigstore publication until a fresh artifact exists. No stale artifact may be signed.

## Target dual-publish contract

```text
frozen pipeline snapshot
  → probe + evidence generation
  → fresh canonical daily artifact
       ├── existing Ed25519 envelope/chain-head path
       └── SHA-256 digest
            → Cosign ECDSA P-256 via `openbao://...`
            → consistency-aware Rekor adapter
            → private trusted-root verified bundle
  → additive dated bundle/reference publication
```

Required invariants:

- both backends name the identical canonical artifact digest;
- existing Ed25519 `L1` and optional Git-tag `L2` meanings remain unchanged;
- Sigstore status is additive and identifies backend, digest, log identity/index, and inclusion evidence;
- OpenBao/Rekor outage fails the new backend closed but does not invalidate a valid legacy result;
- no raw national-data payload is sent to Rekor beyond the selected canonical artifact required by the bundle;
- no retry of a successful Rekor POST; adapter polls GET-only and fails closed;
- trusted-root distribution is explicit and operator-controlled;
- bundle and trust metadata are retained with dated evidence artifacts;
- rollback stops new publishing/consumption without deleting legacy envelopes, bundles, keys, or Rekor records.
