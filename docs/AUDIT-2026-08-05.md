## Summary

**Documentation health: 4/10.** The catalogue size, licence split, namespace
split, MCP version, and MCP tool list are consistent across the main discovery
surfaces. The project nevertheless has several trust-breaking contradictions:

1. The README health distribution is already two datasets behind the live
   health file, and its “weekly monitoring” description omits the primary
   15-minute tiered VPS timer.
2. The public manifest fails its own declared JSON Schema for all 122 entries.
3. `changelog.json`, the Markdown changelog, contribution rules, JSON-LD URLs,
   and parts of the generated OpenWiki are materially stale.

The three most-stale files in the requested root/`docs/` inventory are:

1. **`CHANGELOG.md`** — still describes an initial seven-dataset, three-agency
   release and contains no record of the expansion to 122 datasets, GTFS,
   eight statuses, MCP, agent discovery, tiered checks, or the custom domain.
2. **`changelog.json`** — advertises the old `80 fresh / 25 aging / 11 stale /
   5 browser-dependent / 1 unreachable` state, has no degraded or
   unknown-freshness counts, and has not been generated since August 4.
3. **`CONTRIBUTING.md`** — requires the obsolete `healthy/degraded/unavailable`
   taxonomy, omits required/current manifest fields, and promises a three-file
   contribution contract that no longer describes the deployed artifact set.

There is a second critical stale-doc cluster outside the inventory boundary:
`openwiki/datasets.md`, `openwiki/operations.md`, and `openwiki/quickstart.md`
still describe the old status taxonomy, weekly-only checks, 80/12 licence
split, 85 direct + 7 browser datasets, and pre-GTFS probe paths. These should be
regenerated in the same docs push.

### Highest-risk findings

- **Declared schema is false:** `python3 -m jsonschema -i datapulse.json
  datapulse.schema.json` exits 1. Every entry has at least `real_status`, and
  121 also have `verified_at`; the schema forbids both. Six entries add
  `probe_note`, and the discontinued Kuantan entry adds
  `discontinued_reason`.
- **JSON-LD links are broken:** the catalog contains 122 dataset entries, but
  all 122 `url`/`contentUrl` values omit `.md` and return 404. The dashboard's
  static JSON-LD includes only 50 per-dataset objects, not 122.
- **The README generator is not part of the effective live timer:** the repo
  service calls `gen_readme_summary.sh`, but the installed service and dotfiles
  source do not. That explains why health moves while README counts remain
  fixed.
- **Public discovery has three broken URLs:** the MCP schema URL returns 404,
  the JSON-LD context URL returns 404, and `llms.txt` links to
  `/docs/mcp-deploy.md` even though Pages serves `/mcp-deploy.md`.
- **Machine changelog has no regeneration path:** no script or workflow builds
  `changelog.json` from the current manifest/health state.

### What exists versus what this project needs

What exists is strong at the dataset layer: 122 Markdown health reports, 92
JSON envelopes, 122 per-dataset JSON-LD files plus one catalog, samples, a
dashboard, discovery manifests, an MCP implementation, generated health/badges/
RSS, and deploy configuration. What is weak is the maintained connective
documentation: architecture, operations, methodology, schema evolution,
security, and release ownership are either absent or trapped in Honcho/OpenWiki
text that does not track the running system.

The 30 GTFS datasets have Markdown reports and JSON-LD, but no matching
`data/json/<id>.json` envelopes. That directly contradicts the universal
three-file model in `CONTRIBUTING.md` and should be resolved as either an
explicit GTFS exception or an artifact-generation gap.

10. **Only then update release history and directory drafts.** Recompute commit

## Appendix — Honcho durable facts absent from canonical docs

The requested Honcho session returned all 47 messages. The following facts are
durable architectural decisions, failure modes, or operating rules that remain
missing from root/`docs/` canonical documentation. Values in parentheses were
independently rechecked during this audit where possible.

1. The primary health runner is an enabled 15-minute systemd timer; `--due`
   maps refresh frequencies to probe tiers. Current manifest grouping is 17
   hourly/30-second datasets, 4 weekday-timed BNM datasets rechecked hourly, 7
   daily, 32 weekly/monthly/quarterly, and 62 slow datasets.
2. GitHub Actions is a weekly full-probe fallback. VPS execution is required
   for the five Camofox datasets because the sidecar is Tailscale-only.
3. Browser probes must be serialized against the single browser instance.
   Direct HTTP probes can remain parallel. An isolated smoke-test pass does not
   prove the production shared-resource path will pass.
4. Slow rendered pages need polling with a hard deadline, not a single sleep
   and fetch or repeated timeout inflation. “Camofox unavailable,” “snapshot
   failed,” “no tab id,” and “no snapshot” describe different failures.
5. A failed probe that measured nothing must not erase the previous successful
   measurement. The system preserves `last_checked`; a future improvement is a
   `consecutive_failures` signal so preserved timestamps do not look silently
   stuck.
6. Browser-extracted dates must reject future dates because tender close dates
   can otherwise masquerade as publication freshness.
7. Rolling filenames such as PriceCatcher must be resolved at probe time. The
   human manifest URL can remain canonical, but docs must explain the effective
   request URL distinction.
8. Dataset name and declared cadence must agree. “Daily” in the former
   PriceCatcher title contradicted its monthly release cadence.
9. The direct data.gov.my/OpenDOSM API paths were replaced for many datasets by
   storage-host CSV/Parquet URLs after redirects/decommissioning; probe method
   and manifest URL migrations need a documented policy.
10. Timer runs must log a start and finish even when nothing changes. A silent
    no-op is operationally indistinguishable from a timer that never fired.
11. `git pull --rebase --autostash` is acceptable for the fully automated timer,
    but not a blanket recommendation for human development workflows.
12. Two working trees (`/home/redza/datapulse-my` for the timer and
    `/tmp/datapulse-my-vps` for dispatches) are the dominant deployment hazard.
    The structural fix is one canonical working directory; autostash is only a
    mitigation.
13. Health push → `deploy-pages.yml` → Pages is the intended publication chain;
    `workflow_run` exists because a workflow's `GITHUB_TOKEN` push does not
    trigger ordinary push workflows.
14. The operational failure taxonomy should document at least: direct curl
    failure, HTTP 404/discontinued, browser unavailable, snapshot timeout,
    missing tab/snapshot, internal expected-result mismatch, and silent timer
    failure.
15. “Reachable,” “content current,” and “snapshot recently generated” are
    separate statements. Dashboard cards and prose should expose dataset
    staleness even when the endpoint itself is alive.
16. There are 121 live manifest sources and one deliberately retained
    discontinued source (`gtfs_static_prasarana_bus_kuantan`), which explains
    the single unreachable row.
17. Record-count coverage is now 116/122, not the earlier 17/122 or 21/122
    snapshots in planning text. The remaining six and the 18 no-freshness-signal
    datasets are durable quality gaps worth exposing.
18. Production artifact ownership is split today: installed systemd/dotfiles,
    repo deploy templates, Cloudflare dashboard token configuration, and GitHub
    workflows do not fully agree. Canonical ownership must be decided and
    documented.
